# R2 12슬롯 재진입 20건 파일럿

## 1. 결론

분류 1·2의 다중방법 성공 763건을 곧바로 KOSIS에 보내지 않고, 고정된 대표 20건으로
`문맥 포함 구조화 -> 12슬롯 보완 -> 원문 수치 역추적 -> 목표 역할·수치·단위 대조`를 먼저
실행했다. 최종 v2에서 R3 투입 가능은 4건, HOLD는 16건이었다. KOSIS는 0회 호출했다.

이 결과는 12슬롯을 모두 느슨하게 만드는 것이 해결책이 아님을 보여준다. 조건부 슬롯은
기사에 없으면 비워 둘 수 있지만, KOSIS 좌표를 결정하는 지표·값·목표값 역할·단위·기간·주기·
계산은 근거 없이 채우거나 생략해서는 안 된다. 따라서 763건 전체 공급자 호출과 KOSIS 조회는
아직 진행하지 않는다.

## 2. 학습 구간과 질문

- 구간: A(R1-R2)
- 고정 입력: `r2_12slot_reentry_queue.jsonl` 763건
- 질문: 문맥 보완 Claim과 검증된 자식 Claim을 12슬롯으로 재구성했을 때, 어느 Claim만
  안전하게 R3에 보낼 수 있는가?
- 정확도 경계: 연결된 독립 12슬롯 Gold가 없으므로 `NOT_EVALUABLE_NO_LINKED_12SLOT_GOLD`
- 운영 지표: R3_READY/HOLD/API_ERROR는 통과 범위이며 정확도가 아니다.

## 3. 표본 고정 방법

`tools.build_r2_12slot_reentry_pilot`은 Claim ID SHA-256 순서로 문맥 보완 10건을 선택하고,
자식 Claim 10건은 목표값 역할을 먼저 한 건씩 포함한 뒤 SHA-256 순서로 채운다.

| 표본 | 건수 |
|---|---:|
| 문맥 보완 부모 Claim | 10 |
| 검증된 원자 자식 Claim | 10 |
| 합계 | 20 |

자식 Claim에는 CURRENT, CHANGE, PRIOR, SHARE, THRESHOLD, RANK, RATIO와 함께 스키마에
없는 RANGE_VALUE 한 건을 음성 대조군으로 포함했다. 문맥 표본에는 KOSIS 주기로 바로 쓸 수
없는 `부분기간` 두 건도 포함했다.

## 4. 안전문

공급자 호출은 Claim당 한 번이며 자동 재시도하지 않는다. 공급자에게는 검증 문장, 작성일,
앞뒤 문맥을 함께 주지만, 다음 검사는 Python에서 결정적으로 다시 수행한다.

1. 구조화 출력이 ClaimSchema 계약을 지키는가?
2. 필수 7개 제어 슬롯이 존재하는가?
3. 선택한 값이 검증 대상 문장에 실제로 있는가?
4. 지표가 검증 문장 또는 제공된 문맥에 실제로 있는가?
5. 문맥에서 확정한 기간·주기와 공급자 결과가 충돌하지 않는가?
6. 자식 Claim은 기존 목표값 역할·수치·단위와 모두 일치하는가?
7. 하나라도 실패하면 HOLD하고 KOSIS를 호출하지 않는가?

문맥에서 확정한 time/frequency는 공급자 출력이 비었을 때만 보완한다. 서로 다른 값이 있으면
덮어쓰지 않고 HOLD한다. `부분기간`은 일반 월·년 주기로 바꾸지 않는다.

## 5. failing test와 최소 변경

초기 실험에서 같은 연도인 `2025`와 `2025년`을 문맥 충돌로 처리하는 결함을 발견했다.
두 표기가 동일하게 처리되어야 한다는 테스트를 먼저 추가했고 실제 HOLD 실패를 확인했다.
그 뒤 연도 표기 정규화 한 곳만 수정했다.

추가 안전 테스트는 다음을 고정한다.

- 정상 문맥 기간 보완과 정상 자식 목표값은 R3_READY
- ClaimSchema에 없는 RANGE_VALUE는 HOLD
- `부분기간`을 일반 KOSIS 주기로 위장하지 않고 HOLD
- `YYYY`와 `YYYY년`은 같은 연도로 취급
- 실행 간 비교는 저장 결과만 읽고 공급자와 KOSIS를 다시 호출하지 않음

## 6. 실제 실행 결과

### v1: 결함 수정 전 보존 실행

| 상태 | 건수 |
|---|---:|
| R3_READY | 3 |
| HOLD | 14 |

HTTP 429 세 건을 성공으로 바꾸거나 자동 재시도하지 않았다. 이 실행은 실패 시도 증거로 남겼다.

### v2: 연도 표기 수정 후 동일 표본 재평가

| 상태/사유 | 건수 |
|---|---:|
| R3_READY | 4 |
| 문맥 기간·주기 충돌 | 8 |
| 공급자 필수슬롯/검토 상태 | 3 |
| 원문 수치 역추적 실패 | 3 |
| 목표값 역할 불일치 | 2 |

R3_READY 4건은 필수슬롯, 원문 값, 지표 근거, 문맥 일관성, 자식 목표값 검사를 모두 통과했다.
이는 20% 운영 통과율이지 20% 정확도가 아니다.

### 두 실행 비교

두 실행 모두 공급자 응답을 확보한 17건 중 최종 ClaimSchema가 완전히 달라진 행은 4건
(23.5%)이었다. 최종 상태가 달라진 행은 세 건이며, 한 건은 의도한 연도 정규화 효과이고
두 건은 공급자 구조화 출력 차이였다. 따라서 단일 호출 결과만으로 763건 전체를 안전하게
확장할 근거가 부족하다.
