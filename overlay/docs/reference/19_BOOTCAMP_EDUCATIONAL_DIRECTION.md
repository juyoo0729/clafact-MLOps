# CLAFACT 부트캠프 교육 방향과 학습 계약

## 1. 방향 전환

CLAFACT의 1차 목표를 "실시간 뉴스 서비스 운영"에서 "복잡한 AI 파이프라인을 구간별로
진단하고, 한 가지 개선을 재현 가능한 증거로 설명하는 학습 프로젝트"로 전환한다.

서비스 화면과 E2E 데모는 결과를 보여주는 보조 수단이다. 프로젝트 완성의 핵심은 다음 질문에
답할 수 있는가이다.

1. 처음에는 어디에서 왜 실패했는가?
2. 어떤 가설을 세웠고 어떤 테스트가 먼저 실패했는가?
3. 무엇 하나를 바꿨는가?
4. 같은 입력과 같은 scorer에서 얼마나 달라졌는가?
5. 무엇은 아직 측정할 수 없고 왜 그런가?

이 방향은 2026-08-22 내부 Notion의 팩트체크 파이프라인 멘토링 세션 권고를 반영한다.
멘토링에서는 구간별 모듈화와 입출력 로그, 이틀 단위 개선 사이클,
맞춤 평가 지표, 반복 측정, 그리고 절대 점수보다 개선 과정을 주요 완성 기준으로 제시했다.

## 2. 교육 목표

### 목표 1: 문제를 측정 가능한 구간으로 나눈다

멘토링의 A/B/C 구간을 이 프로젝트에서는 다음처럼 매핑한다. 이는 교육 운영을 위한 저장소의
매핑이며, 원래 멘토링 발언에 없던 세부 경계를 임의의 사실처럼 주장하지 않는다.

| 구간 | CLAFACT 단계 | 학습 질문 | 대표 산출물 |
|---|---|---|---|
| A: Claim 구조화 | R1-R2 | 기사 문장에서 검증 가능한 Claim과 12-slot IR을 얼마나 안정적으로 만드는가? | 후보/READY/HOLD, slot 오류표 |
| B: 통계표 탐색 | R3 | 구조화 Claim에 맞는 KOSIS 표를 Hard Guard 이후 얼마나 잘 찾는가? | ranked candidates, Hit@k, HOLD reason |
| C: 근거와 판정 | R4 | 동일 표의 정확한 좌표·공식값·계산으로 재현 가능한 Verdict를 만드는가? | Evidence Cell, coordinate exact, Verdict |

각 구간은 저장된 입력으로 독립 실행할 수 있어야 하며, 입력·출력·실패 사유를 다음 구간과
분리해 보존한다.

### 목표 2: TDD로 한 번에 한 변수만 바꾼다

모든 개선은 아래 계약을 지킨다.

1. 고정된 입력과 기준선 결과를 선택한다.
2. 실패 유형 하나를 선택하고 한 문장 가설을 쓴다.
3. 기대 동작을 표현하는 failing test를 먼저 추가하고 실패를 확인한다.
4. prompt, normalizer, rule, postprocess 중 한 요소만 최소 수정한다.
5. 관련 테스트와 동일 scorer를 다시 실행한다.
6. 개선·퇴행·변화 없음 중 하나로 결론을 내리고 실패 시도도 남긴다.

Gold 변경, prediction 변환, threshold 완화로 점수를 맞추는 것은 개선이 아니다. 비교 중에는
locked test를 사용하지 않고 고정 dev만 사용한다.

### 목표 3: 평가를 설계하고 한계를 설명한다

| 종류 | 의미 | 발표에서의 사용 |
|---|---|---|
| 학습 과정 지표 | 재현 가능한 실험 수, failing test 증거, 단일 변경 준수, 오류 원인 설명 | 프로젝트 수행 역량 |
| Gold 성능 지표 | 같은 ID/hash로 조인된 정확도·F1·Hit@k·exact | 모델/파이프라인 성능 |
| 운영 지표 | 처리 건수, AUTO/HOLD 비율, API 성공률·비용·시간 | 데모 안정성·비용 관찰 |

운영 coverage를 정확도로 부르지 않는다. 독립 Gold가 없거나 cohort가 다르면
`NOT_EVALUABLE`과 reason code를 유지한다. R1 `UNCERTAIN`은 FALSE가 아니며, R3/R4 claim ID
조인이 0이면 점수를 만들지 않는다.

비결정론적 LLM 비교가 필요한 경우 동일 설정을 3-5회 반복하고 평균과 표준편차를 함께 제시한다.
단, 비용·속도 최적화는 먼저 정한 품질 목표를 만족한 뒤의 2차 목표다.

### 목표 4: 책임 있는 AI/MLOps를 경험한다

- `HOLD`는 근거 부족을 숨기지 않는 안전한 출력이다.
- manifest, prediction, evaluation, SHA-256은 덮어쓰지 않고 새 ID로 남긴다.
- 기사 원문·URL·API 키·원시 provider 응답은 외부 요약에 넣지 않는다.
- 자동 재시도, 자동학습, Gold 자동 수정, 코드 자동 적용을 하지 않는다.
- FlyHermes는 저장된 실험을 재현하고 count-only 결과를 남기는 실습 환경으로 사용한다.

## 3. 이틀 단위 학습 사이클

### 1일차: 관찰과 가설

- 최신 고정 평가와 error queue를 읽는다.
- A/B/C 중 한 구간과 가장 큰 실패 유형 하나를 고른다.
- 기준선, 학습 질문, 기대 효과, 퇴행 위험을 기록한다.
- 최소 failing test를 작성하고 실패 증거를 남긴다.

### 2일차: 최소 개선과 회고

- 승인된 한 요소만 수정한다.
- 단위 테스트와 동일 고정 평가를 실행한다.
- 기준선과 개선값, 오류 분포, 새 퇴행을 비교한다.
- `IMPROVED`, `NOT_IMPROVED`, `NOT_EVALUABLE` 중 하나로 결론을 낸다.
- 다음 사이클에서 검증할 질문 하나만 남긴다.

## 4. 필수 학습 산출물

각 사이클은 아래 자료를 새 ID의 불변 디렉터리에 보존한다.

```text
learning_runs/<learning_run_id>/
  learning_summary.json       # 구간, 학습 질문, 기준선, 결론
  experiment_card.md          # 가설, 단일 변경, TDD 증거, 회고
  metric_comparison.json      # 비교 가능한 지표만 before/after
  error_analysis.json         # count-only 오류 유형과 퇴행
  sha256_manifest.json        # 입력·출력 무결성
  safe_summary.txt            # 비밀·기사 내용이 없는 발표용 요약
```

현재 도구가 위 파일을 모두 자동 생성하지 못하는 경우 기존 evaluation/experiment artifact의
경로와 SHA-256을 참조하고, 없는 항목은 `NOT_PRODUCED`로 명시한다. 존재하지 않는 증거를 만들지 않는다.

## 5. 발표 구성

10-15분 발표의 본문은 다음 순서를 사용한다.

1. 왜 뉴스 수치 주장과 KOSIS를 연결하기 어려운가
2. R1-R4와 교육용 A/B/C 구간을 어떻게 설계했는가
3. 구간별 초기 성능과 가장 큰 병목은 무엇이었는가
4. TDD로 무엇을 시도했고 무엇이 실패했는가
5. 같은 계약에서 무엇이 얼마나 개선되었는가
6. HOLD/NOT_EVALUABLE을 왜 보존했는가
7. 남은 한계와 다음 한 가지 실험은 무엇인가

KOSIS API 구조, 배포 환경, 상세 운영 명령은 부록으로 이동한다. 데모는 E2E와 중간 단계의
입출력·HOLD 사유가 보이도록 구성하되, 데모 성공 자체를 정확도 증거로 사용하지 않는다.

## 6. 일정 기준

- 2026-09-02까지: A/B/C 구간 개선과 평가 증거 확정
- 2026-09-03부터: 발표 자료, 데모 영상, 부록 제작
- 2026-09-09: 최종 발표

일정이 변경되어도 순서는 유지한다. 개선 실험을 마치기 전에 서비스 기능을 늘리거나 발표 장식을
우선하지 않는다.

## 7. 현재 보류하는 서비스 과제

아래 항목은 필요하지만 핵심 구간의 품질 목표와 학습 증거가 확보된 뒤 다루는 2차 과제다.

- 새 RSS 출처 확대와 실시간 기사 처리량 증대
- KOSIS QPM 대응을 위한 여러 API 키 자동 전환
- 무중단 스케줄, 자동 재시도, 자동학습
- UI 장식, 배포 플랫폼 이동, 데모 로딩 최적화

특히 API 키 폴백은 보안·쿼터·운영 책임이 있는 별도 설계 과제로 둔다. 교육용 평가가 여러 키를
자동 순환하거나 키 값을 읽고 기록하게 하지 않는다.

## 8. 완료 정의

다음 항목을 모두 만족하면 부트캠프 프로젝트로 완료한 것으로 본다.

- 최소 한 구간에서 baseline -> failing test -> 단일 변경 -> 재평가 흐름이 재현된다.
- 개선되지 않은 시도까지 포함해 오류 원인과 판단 근거를 설명할 수 있다.
- 운영 지표와 Gold 성능 지표가 문서와 산출물에서 분리되어 있다.
- 모든 수치는 입력, scorer, split, run ID, SHA-256으로 추적 가능하다.
- 측정할 수 없는 항목은 숫자 대신 `NOT_EVALUABLE`과 이유가 있다.
- 발표가 서비스 기능 목록보다 문제 해결 과정과 배운 점을 중심으로 구성된다.
